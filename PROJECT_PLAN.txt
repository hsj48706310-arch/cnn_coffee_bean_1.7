1. 분류 문제 설계 (Task Definition)
================================================================================
[Task A] 결점두 분류 (Multi-class Classification)
  Classes (예시 6):
    0. normal           (정상두)
    1. broken           (깨짐)
    2. insect_damage    (벌레먹음)
    3. immature         (미성숙/quaker)
    4. black/sour       (흑두/발효두)
    5. husk/foreign     (껍질/이물질)

[Task B] 로스팅 단계 분류 (Ordinal Classification)
  Classes (5):
    0. Green   1. Light   2. Medium   3. Dark   4. Italian
  -> 순서가 있는 라벨이므로 Ordinal Loss / Label Smoothing 고려

[Task C] (확장) 품질 점수 회귀
  - SCA 그린빈 평가 기준 응용 → 0~100 점수 예측 (Regression head)

>>> MVP 단계에서는 Task A + Task B (Multi-Task CNN 1개) 로 진행 권장.
    하나의 backbone + 두 개의 head (defect_head, roast_head)

3. 모델 설계 - "CNN이 뭔가, 어떤 CNN을 쓸 것인가"
================================================================================
[3-1] CNN(Convolutional Neural Network) 한 줄 정의
  - 이미지의 "지역적 패턴(엣지→텍스처→부분→객체)"을 컨볼루션 필터로
    계층적으로 학습하는 신경망. Conv + Pooling + Activation 반복 구조.

[3-2] CNN 계열 모델 종류 (시대순 흐름)
  1) LeNet-5 (1998)              - 손글씨, 너무 작음(학습 데모용)
  2) AlexNet (2012)              - ImageNet 우승, ReLU/Dropout 도입
  3) VGG16/19 (2014)             - 단순 3x3 conv 반복, 무겁지만 transfer 잘됨
  4) GoogLeNet/Inception (2014)  - Inception module
  5) ResNet18/34/50 (2015)       - Skip connection, **사실상 표준 baseline**
  6) DenseNet (2016)             - dense connection
  7) MobileNetV2/V3 (2018/19)    - Depthwise sep conv, **모바일/CPU 친화**
  8) EfficientNet B0~B7 (2019)   - Compound scaling, 정확도/효율 균형
  9) EfficientNetV2 (2021)       - 학습 속도 ↑
 10) ConvNeXt (2022)             - Transformer 트렌드를 CNN에 역수입, SOTA급
 11) (참고) ViT/Swin             - CNN은 아니지만 비교군으로 자주 사용

[3-3] "내 PC에서 돌아가는" 추천 모델 (로컬 친화)
  GPU 없음(노트북 CPU만):
    ★ MobileNetV3-Small / Large   (param 2.5M / 5.4M, CPU 추론 빠름)
    ★ EfficientNet-B0             (param 5.3M, 정확도 좋음)
    ○ ResNet18                    (param 11.7M, 안정적 baseline)
  GPU 있음(GTX1650 / RTX3060급):
    ★ EfficientNet-B0 ~ B2
    ★ ConvNeXt-Tiny               (param 28M, 정확도 ↑)
    ○ ResNet50

  >>> 본 프로젝트 권장:
      Baseline  : ResNet18  (빠르게 파이프라인 검증)
      Main      : EfficientNet-B0 (transfer learning)
      Light/Demo: MobileNetV3-Small (실시간 웹캠용)

[3-4] 아키텍처 (Multi-Task Head)
  Input(3x224x224)
    └─ Backbone (EfficientNet-B0, pretrained=ImageNet, freeze 후 fine-tune)
        └─ GlobalAvgPool → Feature(1280-d)
            ├─ Head A: Linear(1280→256)→ReLU→Dropout(0.3)→Linear(256→6)  # defect
            └─ Head B: Linear(1280→256)→ReLU→Dropout(0.3)→Linear(256→5)  # roast

  Loss = α * CE(defect) + β * CE(roast)         (α=1.0, β=1.0 → 튜닝)
  - Class imbalance → CrossEntropy(weight=class_weights) or Focal Loss
  - Roast head는 Label Smoothing(0.1) 또는 Ordinal regression(CORAL) 적용

4. 모델 성능 올리는 방법 (Performance Boosting Checklist)
================================================================================
[4-1] 데이터 레벨 (효과 가장 큼!!)
  □ 데이터 양 늘리기 (클래스당 1000+장)
  □ 클래스 균형 맞추기 (오버샘플링 / WeightedRandomSampler)
  □ 강한 증강: MixUp, CutMix, RandAugment, Albumentations
  □ 라벨 노이즈 제거: 직접 검수 + cleanlab 라이브러리
  □ 도메인 일치: 실제 사용 환경(조명/배경)과 동일하게 수집

[4-2] 모델 레벨
  □ Pretrained weights 사용 (timm 라이브러리 강력 추천)
  □ Backbone 단계적 unfreeze (head만 5epoch → 전체 fine-tune)
  □ 더 큰 모델로 점진적 교체 (B0 → B2 → ConvNeXt-Tiny)
  □ Dropout, BatchNorm 위치 점검
  □ Test-Time Augmentation (TTA): flip/rotate 평균

[4-3] 학습 레벨
  □ Optimizer: AdamW (lr=1e-3, weight_decay=1e-4)
  □ Scheduler: CosineAnnealingLR or OneCycleLR
  □ Early Stopping (val_loss patience=7)
  □ Mixed Precision (torch.cuda.amp) → 속도 2배
  □ Gradient Clipping (max_norm=1.0)
  □ K-Fold Cross Validation (최종 5-fold ensemble)

[4-4] 손실/평가 레벨
  □ Class weight 조정
  □ Focal Loss (불균형 심할 때)
  □ Confusion Matrix 보고 클래스별 약점 파악 → 데이터 추가

[4-5] 후처리/배포 레벨
  □ ONNX export → onnxruntime 추론 (CPU에서도 빠름)
  □ Quantization (INT8) → MobileNet에 효과적
  □ Knowledge Distillation: 큰모델(Teacher) → 작은모델(Student)

----- src/dataset.py -----
import torch
from torch.utils.data import Dataset, DataLoader
from PIL import Image
import pandas as pd
import albumentations as A
from albumentations.pytorch import ToTensorV2

class CoffeeBeanDataset(Dataset):
    def __init__(self, csv_path, transform=None):
        self.df = pd.read_csv(csv_path)   # columns: path, defect_label, roast_label
        self.transform = transform

    def __len__(self):
        return len(self.df)

    def __getitem__(self, idx):
        row = self.df.iloc[idx]
        img = np.array(Image.open(row['path']).convert('RGB'))
        if self.transform:
            img = self.transform(image=img)['image']
        return img, int(row['defect_label']), int(row['roast_label'])

def get_transforms(train=True):
    if train:
        return A.Compose([
            A.RandomResizedCrop(224, 224, scale=(0.8,1.0)),
            A.HorizontalFlip(), A.VerticalFlip(),
            A.Rotate(limit=30),
            A.ColorJitter(0.2,0.2,0.1,0.05),    # roast용은 약하게
            A.Normalize(), ToTensorV2(),
        ])
    return A.Compose([A.Resize(224,224), A.Normalize(), ToTensorV2()])


----- src/model.py -----
import torch.nn as nn
import timm

class CoffeeNet(nn.Module):
    def __init__(self, backbone='efficientnet_b0',
                 n_defect=6, n_roast=5, pretrained=True):
        super().__init__()
        self.backbone = timm.create_model(backbone, pretrained=pretrained,
                                          num_classes=0, global_pool='avg')
        feat = self.backbone.num_features
        self.defect_head = nn.Sequential(
            nn.Linear(feat,256), nn.ReLU(), nn.Dropout(0.3),
            nn.Linear(256, n_defect))
        self.roast_head = nn.Sequential(
            nn.Linear(feat,256), nn.ReLU(), nn.Dropout(0.3),
            nn.Linear(256, n_roast))

    def forward(self, x):
        f = self.backbone(x)
        return self.defect_head(f), self.roast_head(f)


----- src/losses.py -----
import torch.nn as nn
class MultiTaskLoss(nn.Module):
    def __init__(self, alpha=1.0, beta=1.0, w_defect=None, w_roast=None):
        super().__init__()
        self.ce_d = nn.CrossEntropyLoss(weight=w_defect, label_smoothing=0.05)
        self.ce_r = nn.CrossEntropyLoss(weight=w_roast,  label_smoothing=0.10)
        self.a, self.b = alpha, beta
    def forward(self, out_d, out_r, y_d, y_r):
        return self.a*self.ce_d(out_d,y_d) + self.b*self.ce_r(out_r,y_r)

       val = evaluate()

import cv2, torch
from src.model import CoffeeNet
from src.dataset import get_transforms

model = CoffeeNet().eval()
model.load_state_dict(torch.load('checkpoints/best.pth', map_location='cpu'))
tf = get_transforms(train=False)
DEFECT = ['normal','broken','insect','immature','black','husk']
ROAST  = ['green','light','medium','dark','italian']

cap = cv2.VideoCapture(0)
while True:
    ok, frame = cap.read()
    if not ok: break
    rgb = cv2.cvtColor(frame, cv2.COLOR_BGR2RGB)
    x = tf(image=rgb)['image'].unsqueeze(0)
    with torch.no_grad():
        od, orr = model(x)
        d = DEFECT[od.argmax(1).item()]
        r = ROAST[orr.argmax(1).item()]
    cv2.putText(frame, f'Defect:{d}  Roast:{r}', (10,30),
                cv2.FONT_HERSHEY_SIMPLEX, 0.8, (0,255,0), 2)
    cv2.imshow('CoffeeBean (q=quit)', frame)
    if cv2.waitKey(1) & 0xFF == ord('q'): break
cap.release(); cv2.destroyAllWindows()

14. 왜 이렇게 설계했는가 (Design Rationale & Alternatives)
================================================================================
"각 선택의 이유 + 다른 방법 + 그래도 이게 더 좋은 이유"를 항목별로 정리.
발표/보고서에서 "왜?"라는 질문에 바로 답하기 위한 근거 모음.

────────────────────────────────────────────────────────────────────────────────
[Q1] 왜 "Multi-task (결점 + 로스팅)" 한 모델로 묶었나?
────────────────────────────────────────────────────────────────────────────────
선택: Backbone 1개 + Head 2개 (defect_head, roast_head)

대안:
  (A) 모델 2개 따로 학습
      - 장점: 구조 단순, 각자 최적화 쉬움
      - 단점: 파라미터 2배, 추론 2번, 데이터 활용 비효율
  (B) Multi-label 단일 head (11개 sigmoid)
      - 단점: 두 task의 의미축이 섞임 (결점=형상, 로스팅=색상)
              서로 다른 feature 강조가 필요한데 한 head에 합치면 흐려짐
  (C) ★ 채택: Multi-task (Hard Parameter Sharing)
      - 공통 feature(원두 윤곽/표면) 공유 → 암묵적 정규화로 과적합 ↓
      - 추론 1회로 두 결과 → 실시간 데모에 유리
      - 데이터 적은 task가 많은 task의 표현을 빌려 씀

왜 더 좋나:
  데이터 부족한 미니프로젝트에서 ROI 최고. Loss 가중치(α,β)만 잘 잡으면
  단일 모델 2개 대비 동등 이상 성능.

────────────────────────────────────────────────────────────────────────────────
[Q2] 왜 EfficientNet-B0를 메인으로? (ViT/ResNet50/MobileNet 두고)
────────────────────────────────────────────────────────────────────────────────
흐름: ResNet18(baseline) → EfficientNet-B0(main) → MobileNetV3(demo)

비교표:
  모델            Param    ImgNet   CPU속도     본 프로젝트 용도
  ResNet18        11.7M    70.0%    빠름        baseline 검증
  ResNet50        25.6M    76.1%    보통        무거움
  MobileNetV3-S    5.4M    75.2%    매우빠름    demo 전용
  EffNet-B0        5.3M    77.7%    빠름        ★ main
  ConvNeXt-T      28.6M    82.1%    보통        여유시 교체
  ViT-B/16          86M    77.9%    느림        데이터 부족시 학습 어려움

왜 EfficientNet-B0가 더 좋은가:
  1) 동일 파라미터 대비 정확도 최상위(Compound scaling 설계)
  2) timm pretrained weight 강력 → 적은 데이터에서도 fine-tune 잘됨
  3) 입력 224x224 표준 → 코드 호환성 ↑
  4) ViT는 데이터 hungry(보통 10만+ 필요), 우리는 클래스당 1~2k → CNN 압승
  5) ConvNeXt-T가 더 정확하지만 4~5배 느리고 메모리 ↑ → 후순위

ResNet18을 baseline으로 따로 두는 이유:
  파이프라인(데이터/Loss/평가) 버그를 빠르게 잡기 위해. 표준 모델이라
  문제 생기면 모델 탓이 아님을 빠르게 확신 가능.

────────────────────────────────────────────────────────────────────────────────
[Q3] 왜 "Pretrained + Fine-tune"인가?
────────────────────────────────────────────────────────────────────────────────
대안:
  (A) From scratch (랜덤 초기화) — 수만 장 필요, 우리는 불가
  (B) Linear probing (backbone freeze, head만) — 빠르나 도메인 갭 있으면 한계
  (C) ★ 2-stage Fine-tune
      Stage1: head warm-up 5 epoch
      Stage2: 전체 unfreeze, lr=1e-4로 미세조정
      - 초기 head가 랜덤이라 바로 풀면 좋은 backbone weight가 망가짐

왜 더 좋나:
  소량 데이터에서 가장 검증된 레시피. Catastrophic forgetting 최소화.

────────────────────────────────────────────────────────────────────────────────
[Q4] 왜 데이터 분할에 "GroupSplit"?
────────────────────────────────────────────────────────────────────────────────
문제: 같은 원두 한 알을 여러 각도로 찍으면 매우 비슷한 "쌍둥이" 이미지가
      다수. Random split 하면 train/test에 같이 들어가 → test acc 과대평가.

대안:
  (A) Random split — 간단하나 leakage 위험
  (B) Stratified — 클래스 비율만 맞춤, leakage 못 막음
  (C) ★ StratifiedGroupKFold — "촬영 세션 ID"를 group으로, 클래스 균형 유지

왜 더 좋나:
  실제 배포 환경(처음 보는 원두)의 성능을 정직하게 측정.
  "Kaggle 99% → 실전 60%" 사고 방지.

────────────────────────────────────────────────────────────────────────────────
[Q5] 왜 Augmentation을 task별로 다르게?
────────────────────────────────────────────────────────────────────────────────
핵심: 로스팅 라벨은 "색"이다. ColorJitter 강하면 Light가 Dark처럼 보여
      라벨과 모순 → 모델 혼란.

선택:
  - 결점 분류용: 색 변화 OK (saturation, brightness 강하게)
  - 로스팅 분류용: 색 보존, 기하 변환 위주 (flip, rotate, crop)
  - 공유 backbone: 약한 ColorJitter(0.1 이하)로 절충

왜 더 좋나:
  Augmentation은 "라벨 불변성(label-preserving)"이 전제. 라벨 깨는 변환은
  노이즈 주입과 같음. 도메인 지식 반영이 마지막 5%를 만든다.

────────────────────────────────────────────────────────────────────────────────
[Q6] 왜 Loss는 CrossEntropy + Label Smoothing? (Focal/Ordinal 두고)
────────────────────────────────────────────────────────────────────────────────
대안:
  - Focal Loss: 극심 불균형(1:100+)에서 효과. 우리(1:5)는 과한 처방.
  - Ordinal/CORAL: 로스팅 순서 라벨에 이론상 적합하나 구현 복잡, +1~2%p
  - ★ Label Smoothing(0.05~0.1): 1줄 추가로 과적합↓ calibration↑ 가성비 최고

왜 더 좋나:
  "단순 baseline → 병목 확인 후 정교한 loss로 교체" 원칙. 미니프로젝트는
  loss 튜닝보다 데이터 품질이 훨씬 영향 큼.

────────────────────────────────────────────────────────────────────────────────
[Q7] 왜 AdamW + CosineLR?
────────────────────────────────────────────────────────────────────────────────
- SGD+Momentum: 대규모 데이터 최강이나 lr 튜닝 까다로움
- Adam: 빠르나 weight decay가 잘못 적용됨(AdamW가 수정)
- ★ AdamW: fine-tune의 표준
- StepLR(수동) vs ★ CosineLR(부드럽게 감소, 항상 무난) vs OneCycle(강력하나 튜닝 필요)

왜 더 좋나:
  "튜닝 없이도 평균 이상"이 보장되는 안전한 조합.

────────────────────────────────────────────────────────────────────────────────
[Q8] 왜 MixUp/CutMix?
────────────────────────────────────────────────────────────────────────────────
원리: 이미지+라벨 섞어 학습 → 결정 경계 부드럽게. +1~3%p.
대안: Dropout만(약함), RandAugment(라벨 깰 위험)
★ MixUp(전역 색 분포) + CutMix(부분 텍스처) 병행
주의: 로스팅 task엔 MixUp이 색 평균내므로 α≤0.2.

왜 더 좋나:
  코드 몇 줄로 일반화 성능 향상되는 "공짜 점심"에 가까움.

────────────────────────────────────────────────────────────────────────────────
[Q9] 왜 OpenCV + 자체 추론 루프? (YOLO/MediaPipe 두고)
────────────────────────────────────────────────────────────────────────────────
- YOLOv8: 강력하나 우리 task에 과함, AGPL 라이선스 이슈
- MediaPipe: 사람(hand/face/pose) 특화, 원두 도메인엔 부적합
- ★ PyTorch + OpenCV 직접: 수업 프레임워크(read→preprocess→infer→draw) 그대로
  재사용, 모델 자유 교체, 학습 효과 ↑

왜 더 좋나:
  내가 학습한 CNN을 그대로 통합 가능. 발표/면접에서 "내 파이프라인" 어필.

────────────────────────────────────────────────────────────────────────────────
[Q10] 왜 ONNX 내보내기?
────────────────────────────────────────────────────────────────────────────────
- PyTorch 그대로: 의존성 무거움(~2GB), CPU 추론 느림
- TorchScript: 호환 OK, 속도 향상 제한
- ★ ONNX + onnxruntime: CPU 1.5~3배↑, 가벼움, INT8 quantization 가능
- TensorRT: GPU 최강이나 NVIDIA 종속

왜 더 좋나:
  "노트북 CPU 30FPS" 목표에 가장 합리적.

────────────────────────────────────────────────────────────────────────────────
[Q11] 왜 timm 라이브러리?
────────────────────────────────────────────────────────────────────────────────
- torchvision.models: 안정적이나 모델 종류 적음
- HuggingFace transformers: ViT 풍부, CNN 약함
- ★ timm: CNN/ViT 1000+ 모델, 한 줄로 backbone 교체

왜 더 좋나:
  `timm.create_model('이름', pretrained=True, num_classes=0)` 한 줄로
  모델 교체 → ablation 실험 생산성 압도적.

────────────────────────────────────────────────────────────────────────────────
[Q12] 왜 Streamlit? (Flask/FastAPI/Gradio 두고)
────────────────────────────────────────────────────────────────────────────────
- Flask/FastAPI: API용, 별도 프론트 필요
- Gradio: 매우 간단하나 커스텀 자유도 ↓
- ★ Streamlit: Python만으로 UI/차트/업로드 → 데모 MVP 최적

왜 더 좋나:
  서비스 배포가 아닌 "결과 시각화 + 시연"이 목적. 가장 빠른 MVP.

────────────────────────────────────────────────────────────────────────────────
[Q13] 왜 GradCAM?
────────────────────────────────────────────────────────────────────────────────
모델이 원두를 보는지 배경 그림자를 보는지 시각 검증 → bias/leakage 잡기.
대안 SHAP/LIME/IG는 더 정밀하나 계산비용 ↑, CNN엔 GradCAM이 가장 직관적.

왜 더 좋나:
  "성능 숫자만 말고 근거를 보여라"는 발표/보고서 가산점 포인트.

────────────────────────────────────────────────────────────────────────────────
[정리] 본 설계의 일관된 철학
────────────────────────────────────────────────────────────────────────────────
1) "데이터 적음 + 로컬 PC + 짧은 일정" 제약을 항상 우선
2) 검증된 표준(ResNet, EfficientNet, AdamW, CosineLR, CE+LS)부터 시작
3) 화려한 SOTA(ViT, ConvNeXt-L, Focal, OrdinalLoss)는 병목 확인 후 도입
4) 도메인 지식(색=로스팅 라벨)을 augmentation/loss에 반영
5) 재현성(seed, config, GroupSplit) > 단발성 고득점
6) 발표용 근거(GradCAM, Confusion Matrix, ablation 표)를 처음부터 설계
